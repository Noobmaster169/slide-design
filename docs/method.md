# Method

A deck is read at a glance and executed by a machine. These seven steps are the repeatable part.

1. **Collect the facts.** Every number, name and example traces to a source you can point at.
   Anything unverifiable is cut or marked as a placeholder.
2. **One message per slide.** Write the deck as a list of one-sentence claims before touching
   layout. Two slides with the same claim become one slide.
3. **Pick a layout per slide** from `layouts.md` rather than inventing one.
4. **Build the shell.** `slides new my-deck`, then edit `deck.html`. Tokens live in `tokens.json`.
5. **Draw only what a picture explains better than a sentence.** Use one kit per slide
   (`diagrams.md`). Diagrams are generated by scripts so they can be edited later.
6. **Render and look.** `slides render . --png`, then open every image. A machine cannot tell you
   the slide makes its point; you have to look.
7. **Check.** `slides check .` measures the rendered deck. Fix errors, re-render, look again.

## Why generated diagrams

A diagram that was hand-nudged in a vector editor is frozen: the next edit re-breaks it. A diagram
produced by a script with computed coordinates can be changed in a minute, reviewed in a diff, and
regenerated when the theme changes.

## Working loop for a drawn slide

```bash
python3 diagrams/03-architecture.py
slides inject '<!-- 03 architecture' diagrams/03-architecture.svg
slides render . --png && slides check .
```

## What this method does not decide

Story order, the argument, and whether the deck should exist. Those belong to you. A well-built
deck that makes a weak argument is still a weak deck.
